# AGENTS.md

Instructions for AI agents filing GitHub issues on this repo.

## Why this matters

`scripts/generate-changelog.sh` builds release notes by scanning merged PRs for
linked issues, then extracting each issue's `### Satisfaction Criteria`
section verbatim into the changelog. If you don't match this format exactly,
the issue either won't show up in release notes or will show up wrong.

## Creating an issue

`gh issue create` does not support GitHub's YAML issue forms
(`.github/ISSUE_TEMPLATE/feature_request.yaml`) non-interactively. Instead,
write a body file that reproduces the form's rendered structure and pass it
with `--body-file`.

Required heading, verbatim: `### Satisfaction Criteria`. The changelog script
matches this exact string — do not reword it, and do not add anything above
or below it in that section besides the criteria itself.

### Feature request

```
gh issue create \
  --title "[Feature]: <short imperative title>" \
  --label enhancement \
  --body-file body.md
```

`body.md`:

```markdown
### Feature Description

1-3 sentences. What it is and why, no fluff.

### Satisfaction Criteria

- [ ] <single line, phrased as a finished patch note>
```

### Bug report

```
gh issue create \
  --title "[Bug]: <short description>" \
  --label bug \
  --body-file body.md
```

`body.md`:

```markdown
### Bug Description

`path/to/file.go:LINE` — what's wrong, in engineering terms. Include a
**Trigger:** line if there's a concrete input/action that reproduces it.

### Satisfaction Criteria

- [ ] <single line, phrased as a finished patch note>
```

## Satisfaction Criteria rules

- **Exactly one bullet**, not a checklist of sub-tasks. It becomes one
  changelog line when the linked PR merges.
- Phrase it as a completed patch note in past tense, describing the
  user-visible outcome — not the implementation. Write it as if it's already
  shipped: "Fixed X", "Added Y", "Errors now surface as Z" — not "Should fix
  X" or "Investigate Y".
- Keep it out of implementation detail (function names, internal types). The
  Bug/Feature Description section is where technical detail belongs; the
  Satisfaction Criteria line is what a user reads in the release notes.

## Style

- No AI attribution anywhere in the issue (no "Generated by Claude", no
  session links, no signature).
- Keep descriptions short. File paths and line numbers are useful; padding
  is not.
- Labels: `enhancement` for features, `bug` for defects. Both already exist
  in this repo — don't create new ones without asking.
- This repo does not currently accept external PRs, so skip
  contributor-facing language ("I'm willing to submit a PR", contribution
  guidelines, etc.) in issue bodies.
